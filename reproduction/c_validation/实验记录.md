## 1. 实验目标与工作范围

### 1.1 论文核心主张与本次验证对象

Kamae 将 Spark 预处理管道转换为对应的 Keras 预处理模型，目标是让离线批处理和模型服务端使用一致的特征转换逻辑。本次验证的具体问题是：**对于同一拟合管道和相同原始输入，Spark 输出是否与导出的 Keras 模型输出一致。**

大数据处理环节体现在 Spark 对用户、电影、评分表的读取与关联、类别频率统计、词表构建和批量特征转换。C 使用普通电脑的 CPU 和 Spark 本地模式完成正确性验证。

### 1.2 C 实际完成的工作

| 工作 | 实际实施方式 | 验收依据 |
|---|---|---|
| 定义比较方法 | 区分类别精确相等与连续浮点容差，记录形状和 dtype | 明确每项结果如何判定和解释 |
| 按 A 的说明独立复跑 | 执行 A 原始主脚本与校验脚本 | 在本机重新生成产物，原校验全部 PASS |
| 全量跨框架比对 | 新写 validate_full.py，覆盖 MovieLens 1M 全部记录 | 检查样本数、字段、dtype、形状和逐元素误差 |
| 独立扩展 | 新建 Bucketize 管道，测试两种精度和边界值 | 保存全部 32 个案例及两份模型 |
| 定位扩展差异 | 绕过 Kamae 直接调用 TensorFlow 分桶算子 | 核对差异是否可在底层算子复现 |
| 方法改进 | 实现阈值分析、风险守卫和兼容比较的导出模块 | 四方法正确性对照、真实管道回归和 CPU 开销 |
| 数据和文字交接 | 导出 CSV、JSON、图表、章节初稿和详细记录 | B 能根据原始记录引用并检查结论 |

### 1.3 与 A 工作的衔接

A 的 README 明确说明，其校验脚本只检查 128 条记录，全量验证由 C 完成。本次先按 A 的路径重新生成本机结果，再进行全量检验。

`spark_output.parquet` 和 `preprocessing_model.keras` 是运行生成的结果，不是运行前必须从 A 取得的输入。C 成功复跑说明 A 提供的代码路径可执行；同一次拟合所得 Spark/Keras 输出一致，说明所测管道在所测输入下翻译一致。

## 5. 一致性比较与判定方法

为了判断两端输出是否一致，本实验采用以下比较规则。后续组合扩展沿用这些规则。

1. 先按 A 的入口独立生成本机产物，原 128 行校验四个输出必须通过。
2. 全量比较必须覆盖 1,000,209 行，拒绝空输入，不能仅使用前 128 行代替全量。
3. 类别索引、整数及独热编码的 0/1 必须逐元素精确一致。不能以 `allclose` 的浮点容差豁免桶索引或类别索引差异。
4. 一般连续浮点输出的判定阈值为 `abs(a-b) <= 1e-6 + 1e-6*abs(a)`；但本次基线四个输出均是离散特征，因此实际使用更严格的精确相等判定。
5. 记录 Spark 与 Keras 原始形状和 dtype，仅允许去除明确的单元素包装维，不能任意 reshape 后直接宣布通过。
6. 使用 float64 汇总误差，不先将两端都强制降低为 float32。
7. 扩展至少包含一种 A 未使用的预处理操作，保留边界、特殊值及所有反例，并核对保存前后结果。

原始基线不包含一般连续浮点输出；新增连续数值分支的容差验证见第 12 节。

## 8. 全量一致性验证的实现

### 8.1 执行命令与输入

```powershell
& .\reproduction\c_validation\run_c.ps1 -Step full-check
```

执行 `validate_full.py`，默认输入为本次基线生成的 Parquet 目录与 `.keras` 文件，默认批大小为 4096。它直接用 PyArrow 分批读取 Parquet，不将全部记录 collect 到 Spark 驱动端。

### 8.2 同一条记录如何对应

每个批次同时读取四个原始输入字段和对应 Spark 输出。Keras 输入直接来自同一批记录，因此两端逐行对应，无须假定重新读取其他文件时行顺序相同。

按模型输入名称构建字典，不依赖输入列表的偶然排列；要求模型输出为具有字段名的字典，不猜测四个输出的顺序。

### 8.3 dtype 与形状核对

标量索引在 Parquet 读取后表现为 `(batch,)`，Keras 表现为 `(batch, 1)`。两者每条记录都只有一个值，因此允许去除单元素包装维后比较。

职业与类型分别保留 21 维和 6 维特征轴。`logical_values()` 首先检查第一维必须等于批次行数，再移除长度为 1 的包装维；其余逻辑形状必须一致，否则直接报错。

第一完整批次的实际 dtype、原始形状和逻辑形状见自动附录。最后一个批次为 785 行，全量共 245 批；这些批次数由总行数与批大小计算得到，不作为额外运行次数。

### 8.4 比较与误差统计

四个输出均采用 `expected == actual` 精确比较。对每个字段累计：

- 已比较行数、元素数、不一致元素数；
- 最大绝对误差 `max(abs(Spark-Keras))`；
- 平均绝对误差 `sum(abs(Spark-Keras))/元素数`；
- 原始形状、逻辑特征形状和 dtype。

误差计算时转为 float64 汇总，不先把两端强制转为 float32。当前索引和独热值的数值范围可被 float64 精确表示。验证器最多保存 20 个差异样例用于定位；本次基线无差异，因此 examples 为空。

### 8.5 判定条件与结果文件

必须同时满足“实际总行数等于 1,000,209”和“四个输出不一致元素数均为 0”，才写入总体 `passed=true`。

结果输出为 `results/full_parity.json` 和 `results/full_parity.csv`。本次全量比较 29,006,061 个输出元素，所有不一致数和误差指标均为 0；完整逐字段表见自动附录。

## 9. 独立分桶扩展实验设计

### 9.1 为什么选择 Bucketize

A 基线主要包含字符串、类别索引和独热编码。C 选择其未使用的内置 `BucketizeTransformer`，考察数值输入在分桶边界附近是否仍保持一致。该实验拓展了算子和输入类型，同时可以在 CPU 上用少量、含义明确的测试值定位差异。

### 9.2 管道与参数

```python
pipeline = KamaeSparkPipeline(stages=[
    BucketizeTransformer(
        inputCol="x", outputCol="bucket",
        inputDtype=alias, outputDtype="bigint",
        layerName=f"c_bucket_{dtype}",
        splits=[0.0, 0.1, 1.0],
    )
])
```

其中 float32 对应 Spark `FloatType` 和 inputDtype=`float`；float64 对应 `DoubleType` 和 inputDtype=`double`。Keras 输入类型分别明确为 float32、float64，shape=(1,)。

本实现使用的桶索引从 1 开始，0 留给 padding。有限普通数值的预期区间为：

| 值所在区间 | 桶索引 |
|---|---:|
| 小于 0 | 1 |
| 大于等于 0 且小于 0.1 | 2 |
| 大于等于 0.1 且小于 1 | 3 |
| 大于等于 1 | 4 |

这描述的是本项目 Kamae Transformer 的规则，不能与其他 API 中从 0 开始的桶编号混用。NaN 单独实测，不由上表推导。

### 9.3 输入案例构造

每种精度包含 16 个案例：

| 类别 | 案例数量/精度 | 构造方式 |
|---|---:|---|
| 常规值 | 4 | -2、0.05、0.5、2 |
| 边界及相邻值 | 9 | 对 0、0.1、1 各取左邻、该精度表示的边界、右邻 |
| 正负无穷 | 2 | -inf、inf |
| NaN | 1 | 单独记录其桶编号 |

相邻值通过 NumPy `nextafter` 在对应精度下产生。例如 float32 的“0.1 边界值”是 `0.10000000149011612`，不能与 float64 的 `0.1` 当作完全相同的数值。CSV 保留完整十进制文本，图中的简写仅用于显示。

两种精度共 32 个确定性测试案例，没有随机训练、随机种子重复或统计抽样，因此不计算置信区间。

### 9.4 执行和保存重载检查

```powershell

```

每个案例用 id 标识，Spark 输出按 id 排序后与相同输入的 Keras 输出逐项比较。C 分别构建并导出两个模型：

```text

```

```

```

同时记录张量回读数值、原始 TensorFlow 桶编号、Keras 桶编号以及二者是否一致。实际 `all_raw_tf_match_keras=true`，说明 32 个案例的 Keras 结果均可在 TensorFlow 原始算子路径重现。

结合同一模型保存前后结果均相同，可排除“保存重载改变了输出”这一解释。

### 10.4 已支持的解释与待验证部分

Kamae 的 Keras 分桶层直接调用上述 TensorFlow 算子，Spark 分桶端基于输入与各阈值的比较累加桶编号。float32 中 0.1 的实际表示为 `0.10000000149011612`；float64 的 `0.1` 和其右邻仍小于这一值。观测到的两个 float64 反例与两端分桶阈值精度不同相符。

负的非正规数案例在 TensorFlow 张量回读中仍能看到其原数值，直接分桶却与 Spark 不同。已有证据将差异定位到本机 TensorFlow 算子路径，但尚未通过单独的 CPU 指令或编译选项实验确定更底层原因。因此没有把这两个反例统一归因为“float64 转 float32”。

没有修改 Kamae 或 TensorFlow 来消除反例，也没有调整阈值、删除失败输入或把它们计为通过。

## 13. 精度感知导出：从问题发现到方法实现与验证

### 13.1 从整个复现与扩展实验得到的问题链

A 完成 MovieLens 五阶段管道、版本适配和 128 行校验后，C 在独立 CPU 环境重新运行该流程，并将比较扩大到全部 1,000,209 行、29,006,061 个输出元素，确认原基线四个输出完全一致。

C 继续围绕同一个跨框架一致性问题，完成训练/测试隔离、未知类别、多算子组合和数值边界等验证。整体实验表明，常规数据、冻结参数后的新数据和未知类别场景满足既定比较标准，但在特定浮点边界输入上出现了离散桶编号差异。四个已知反例的具体触发位置是数值分桶，原始基线和七组真实数据比较结果保持成立。

因此，本工作从“验证是否一致”推进到“对已发现的精度风险如何处理”：提出精度感知导出策略，以当前出现差异的浮点分桶算子为实现对象，增加阈值分析、运行时风险守卫和兼容计算路径，再检验正确性、原管道回归与 CPU 开销。

### 13.2 问题机制与方法目标

Spark 参考实现按输入与 double 字面量阈值比较；原始 Keras 路径调用 TensorFlow Bucketize，其阈值采用 float 表示。阈值舍入、上下溢或相邻阈值合并可能改变离散决策。非正规数比较也可能与 Spark 观察到的结果不同，因此单独扩大输入 dtype 不足以解决全部反例。

目标是保留已拟合词表、均值和标准差，仅改变分桶算子的导出实现，使导出图在声明的输入契约内匹配 Spark 的比较语义，同时允许普通输入使用原生路径。本原型处理显式 float32/float64 密集输入、非空且非降序的阈值，拒绝 NaN 阈值；SQL null 不用 NaN 冒充。

### 13.3 提出的方法：导出分析与风险输入路由

#### 13.3.1 导出时分析阈值

转换模块读取已拟合阶段的输入精度、阈值与输出配置，不重新拟合。对 float64 输入保留原 double 阈值；对 float32 输入，将 Spark double 阈值 t 转为“不小于 t 的最小可表示 float32 值”，因为对于可表示的 float32 输入 x，两种比较 x≥t 与 x≥ceil32(t) 等价。

随后比较原生 float 阈值与上述有效阈值：无阈值变化且不涉及零附近风险时保留原生路径；阈值变化时生成风险区间；阈值上下溢、合并、重复或涉及特殊精度条件时采用全量兼容路径。

#### 13.3.2 兼容路径采用 IEEE 有序整数比较

兼容层将浮点的 IEEE 位模式转换为有序整数键 K(x)：保留数值次序，统一正负零，并将 NaN 放在所有非 NaN 数之后，匹配本次 Spark 参考语义。每个阈值用相同方式转换，输出为：

`bucket(x) = 1 + Σ I[K(x) ≥ K(effective_threshold_j)]`

位模式与整数比较避免让极小数再次经过会刷新为零的浮点比较路径。该层由 TensorFlow 图操作组成，不依赖服务时的 Python 回调。

#### 13.3.3 普通输入与风险输入分别执行

对需要守卫的层，运行时用有序键判断输入是否落入阈值变化区间；零阈值附近的非正规数也进入兼容路径。普通输入由原生算子处理，风险位置通过 gather、兼容计算与 scatter 修正。静态分析判断风险较特殊的层使用全量兼容路径。此路由并不保证每种负载都比全量兼容更快，实际开销另行测量。

#### 13.3.4 转换模块与导出产物

实现位于 `precision_aware.py`：`analyse_bucketize` 生成分析结果，`PrecisionBucketizeLayer` 实现三种可选路径，`export_pipeline` 复制已拟合阶段，仅替换分桶层工厂。其他阶段保留原参数，原 Spark 参考实现和 A 的源码保持原样。

导出结果包括 Keras 模型与逐层分析清单。两个自适应分桶模型另导出为 TensorFlow SavedModel，在独立进程中仅加载 TensorFlow 运行原 32 个案例，结果全部一致，且未导入 Kamae 或本原型模块。该检查验证这两个独立分桶图的可执行性，不代表已经部署真实在线服务。
